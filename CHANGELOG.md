# Changelog

## Unreleased

- Repo scaffold: Go tooling (Makefile, golangci-lint, goreleaser, CI/CodeQL/dependabot workflows), LICENSE, SECURITY.md, CONTRIBUTING.md, issue/PR templates.
- Design docs (HANDOFF.md, README.md, docs/VISION.md).
- Step 1 of the evolution path (`actor=app` + `client_credentials` + `createAsUser`/`displayIconUrl`) validated live against a free Linear workspace.
- `internal/watcher`: verifies Linear's `AgentSessionEvent` webhook signature and freshness, dedupes by delivery id, routes to a `Router`.
- `cmd/pennon` now runs the watcher as a real HTTP server (`PENNON_WEBHOOK_SECRET`, `PENNON_LISTEN_ADDR`), graceful shutdown on SIGINT/SIGTERM.
- `internal/watcher.DispatchRouter`: routes events onto mcp-dispatch's `bin/dispatch-send`. `cmd/pennon` uses it when `PENNON_DISPATCH_SEND`/`PENNON_DISPATCH_TO` are set, falling back to `watcher.LogRouter` otherwise. Verified end to end against a real webhook and a real `dispatch-send` binary.
- `internal/watcher` now also decodes Linear's `Issue` webhooks and gates on them: `GateRouter` matches a (team, workflow state) pair against a `GateSet`, checks that the update is a genuine transition into that state (not just any edit while already sitting there), and delegates to the matched specialist via `LinearDelegator` — a real client_credentials mint against the specialist's own OAuth Application followed by `agentSessionCreateOnIssue`. No team, state, or specialist identity is hardcoded anywhere in pennon's source; `cmd/pennon` loads the `GateSet` from a JSON file named by `PENNON_GATE_CONFIG`, and Issue webhooks are acked without action when it's unset (see `config/gate.example.json` for the shape, and docs/ARCHITECTURE.md "Deployment config lives outside pennon's own repo" for where real values belong). Verified end to end: an unmatched team/state acks without delegating, and a matched transition genuinely calls Linear's real token endpoint (confirmed via its `invalid_client` response to intentionally fake test credentials, no real account touched).
- `pennon mint <name>`: mints a `client_credentials` token for an already-registered identity from `~/.config/pennon/identities.json`, granting full `app:mentionable,app:assignable,read,write` scope — a complete replacement for the shared personal API token it's onboarding an agent away from.
- `pennon onboard <name>`: collapses identity onboarding into one command — mints, verifies the token against a live `viewer` query before touching anything, then patches both `.mcp.json` and `.claude/settings.local.json` in place (atomic writes, timestamped backups). Prints what's still manual: reconnecting the MCP server, checking team membership, and reading the host repo's `CLAUDE.md`/`AGENTS.md` for standing operational conventions.
- `pennon onboard-hook <name>`: a `SessionStart` hook that debounces (12h default) and, when due, runs `onboard` detached so a session's own startup never blocks on the mint/verify round-trip. Failures land in a local log rather than surfacing live.
- `docs/loop-templates.md`: two reusable loop-role templates (an orchestrator role and a self-directed agent role) generalized from a real overnight run of a pennon-identified fleet.
- Fixed a real gap found by a resection drift check: `pennon mint`/`onboard` had no code distinguishing a specialist identity from an ordinary fleet agent, so any agent with read access to the shared identities file could mint a specialist's own token. `Specialist` now carries a `Kind` field; `mint`/`onboard` refuse any identity marked `Kind: "specialist"` before ever reaching the network. Also corrected three doc claims (README, docs/ARCHITECTURE.md, CONTRIBUTING.md) that overstated what pennon's code actually enforces around the delegate/assignee split, GitHub branch protection, and "no new credential" — none of those were true code-level guarantees.
- Widened that same fix from specialists to every identity: `onboard` now records the identity it mints in `.claude/settings.local.json`'s `env.PENNON_IDENTITY`, and `mint`/`onboard` refuse to mint any other name once a worktree has declared one — an agent can no longer mint a *different* ordinary agent's token either, not just a specialist's. A fresh, not-yet-onboarded worktree is unaffected; a worktree onboarded before this change is unprotected until its next `onboard` run.
- `pennon gate-poll`: a poll-based stand-in for the watcher's gate, for deployments that don't want to stand up anything reachable from the public internet yet. Reads the same `GateSet` as `GateRouter`, asks Linear which issues currently sit in each gate's (team, state) pair via a new `LinearIssueQuerier`, and delegates any that aren't already delegated to that gate's specialist — checking the issue's live `delegate` field is what keeps repeated poll cycles from re-delegating the same issue, since polling has no webhook `updatedFrom` to diff against. Runs one cycle and exits; meant to be driven by cron, a systemd timer, or a Claude Code `/loop`, not to run as a second daemon. Needs `PENNON_GATE_CONFIG` and its own `PENNON_POLL_TOKEN` (deliberately not a specialist's own credential — listing issues across a team isn't an action taken as that specialist). See docs/ARCHITECTURE.md "Polling instead of the watcher." `LinearIssueQuerier`'s filter shape verified live 2026-09-13 against a real workspace: confirmed the filter genuinely narrows results (checked every returned node's own team/state id, not just a non-error response) and that an unset `delegate` decodes as empty rather than erroring, through the actual Go decode path, not just a raw query.
- Documented a real gap in `docs/ARCHITECTURE.md` "Agent onboarding": `onboard` patches `.mcp.json`'s `linear-notifications` entry if present but never scaffolds it, and no doc said that entry needed to exist first — a fresh adopter following README/ARCHITECTURE alone would have no way to know they needed it, and onboard only warns rather than erroring when it's missing.
- Rewrote `docs/VISION.md` twice: first out of its narrative-essay framing into plain technical prose, then cut down hard after review — the multi-org trust apparatus (reputation ledgers, escrowed bonds, witness co-signatures, cross-org "treaty" documents) described infrastructure this project isn't building, disproportionate to what pennon actually is (per-worktree Linear identity for a personal fleet). What's left states the real near-term plan and points at README's own already-stated scope boundary instead of re-describing the cross-org case in depth.
- Documented a real, checked-live limitation in `internal/watcher/gate.go`'s `Policy` doc comment and `docs/ARCHITECTURE.md` "Trust model": neither of Linear's OAuth-application mutations (`archiveManagedOAuthApplication`, `rotateManagedOAuthApplicationSecret`) apply to pennon's manually-created, standalone identities — both are scoped to "alpha child" apps under a managing parent, which pennon doesn't use. There is no API pennon could call to immediately invalidate an already-issued specialist token; pennon also never reads a specialist's past verdict back, so a revoked or demoted specialist's prior sign-offs stand exactly as posted until Linear's own token expiry. Re-review after revoking a specialist is a manual call for whoever consumes the verdict — not something pennon can detect or enforce, by the same design boundary that keeps veto enforcement outside pennon's own job.
